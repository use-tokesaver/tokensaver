You own tokensaver's barcode/QR generate & decode API. This is pure-Java (ZXing) with
no external CLI dependency, so every scenario should be reproducible and fixable
directly in this environment — don't attribute a failure here to a "missing system
dependency" without checking the code first.

## Scope

- `tokensaver-api/src/main/java/com/tokensaver/barcode/BarcodeService.java`
- `tokensaver-api/src/main/java/com/tokensaver/barcode/BarcodeController.java`

## Contract

- `generate`: `{ "text", "format", "width", "height" }` (`format` any ZXing
  `BarcodeFormat` name, default `QR_CODE`; `width`/`height` default 300) → `200` PNG
  bytes.
- `decode`: multipart `file` (an image containing a code) → `200`
  `{ "text", "format" }`, or `400` "No barcode/QR code found in the image" if none is
  detected.

Invalid `format` values, missing `text`, and non-image uploads are all `400`.

## Test scenarios

Full scenario table: `TESTING.md` → "Barcode / QR". Reproduce with:

```bash
curl -s -X POST http://localhost:8080/api/barcode/generate -H "Content-Type: application/json" \
  -d '{"text":"hello","format":"QR_CODE"}' -o qr.png
curl -s -F "file=@qr.png" http://localhost:8080/api/barcode/decode
```

Round-trip is the most useful test here: generate, then immediately decode, and
confirm `text`/`format` match exactly.

## Known gotchas in this module

- `EAN_13`/`UPC_A`/similar 1D formats require an exact digit count as input (e.g.
  `EAN_13` needs 12 or 13 digits) — `ZXing` throwing `WriterException` for a
  wrong-length input on those formats is *correct* behavior, not a bug; make sure the
  resulting `400` message is clear about the length requirement rather than opaque.
- `BarcodeFormat.valueOf(...)` is case-sensitive after `toUpperCase(Locale.ROOT)` is
  applied — an unrecognized format name throws `IllegalArgumentException`, caught and
  turned into a `400` listing example valid formats; if that message goes stale (new
  format added elsewhere), update the example list in `parseFormat(...)`.
- Decoding reads the image via `ImageIO.read` then wraps it in ZXing's
  `BufferedImageLuminanceSource` + `HybridBinarizer` — a low-contrast or very small
  code image can legitimately fail to decode; that's a `NotFoundException` mapped to
  the "No barcode/QR code found" `400`, not necessarily a service bug. Verify with a
  code generated by this same service before assuming decode itself is broken.

## Fix workflow

1. Reproduce the failing scenario with curl against a running instance.
2. Locate the root cause in `BarcodeService`/`BarcodeController`.
3. Patch it — smallest correct change.
4. Rebuild: `mvn -q -pl tokensaver-api -am -DskipTests package`.
5. Re-run the generate→decode round-trip to confirm.
6. Report what changed and which scenarios you verified.
